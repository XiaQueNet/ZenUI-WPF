# AI 测试工作流

AI 新增、修改或修复测试时，必须同时遵守[测试规范](testing.md)。

## 工作顺序

行为变更或缺陷修复采用：

1. 从现有代码、公开文档或问题描述确认预期行为。
2. 添加能复现缺失行为或缺陷的测试，并确认测试以预期原因失败。
3. 用最小实现使测试通过。
4. 在不降低断言强度的前提下重构。
5. 按[测试规范](testing.md#回归与验证)选择验证等级。组件库的日常新增、修改或删除至少运行受影响的组件测试，并使用 `net472`；改动影响多个组件、共享能力或测试基础设施时，升级为 `net472` 单框架全量测试。

只有改动目标框架配置、跨框架兼容层、构建或打包基础设施，进入发布验证，或者用户明确要求时，才运行全框架矩阵测试。远程 CI 对普通主分支 Push 运行代表性框架，并在 Pull Request 和发布验证中运行完整矩阵；此分层不改变本地验证等级的选择规则。

如果文档、测试和实现互相矛盾，不擅自选择最容易通过的一方。先根据公共 API、兼容性承诺和现有行为判断；仍无法确定时明确指出冲突。

## 测试质量

禁止：

- 修改预期结果来迎合当前实现；
- 使用恒真、空断言或无法触达目标行为的测试；
- 在测试中复制完整生产实现；
- 过度 Mock，导致真实的 WPF 行为、资源、模板或绑定未被执行；
- 只验证内部调用次数，而不验证可观察结果；
- 为无关维护任务重写或搬移大量现有测试。

生产代码尚无可调用入口时，不在测试辅助代码中伪造一套会通过的实现。应让测试清楚暴露缺失的公共行为，或先确认是否确实需要扩展 API。

## 例外

以下任务不要求先得到 Red 状态，但不得降低现有覆盖：

- 重命名或整理测试；
- 修复测试工程、目标框架或 CI 配置；
- 改善测试辅助代码；
- 为已有且稳定的行为补充覆盖；
- 仅修改文档、格式或注释。

完成后简要报告执行过的验证；无法运行的检查应说明原因。
